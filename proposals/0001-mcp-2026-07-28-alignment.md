# Proposal 0001: Align MCP Description with MCP 2026-07-28

- Status: Review
- Author: Stève Sfartz
- Created: 2026-07-28
- Last updated: 2026-08-22
- Target version: 0.8.0
- Related issues: https://github.com/mcpdesc/mcpdesc-specification/issues/3
- Review period: 2026-08-22 through 2026-08-29 (seven calendar days)

## Summary

Update MCP Description for MCP `2026-07-28` by making one document capable of describing deterministic effective contracts for a closed set of MCP protocol revisions.

The proposal keeps mcpdesc focused on durable server semantics rather than MCP wire choreography. It introduces protocol-version scopes, semantic capability modeling, root server instructions, zero-primitive descriptions, and stricter alignment with the MCP Tool model. It also defines projection precisely enough for validators and tools to produce flat, single-protocol documents.

This proposal is intentionally breaking and targets the unreleased 0.8.0 Community Working Draft.

## Review process

The normal review period for potentially breaking changes is at least 30 days. This proposal uses a seven-calendar-day review before a maintainer acceptance decision because the project is in bootstrap, has one maintainer, has no established contributor base, and needs an implementable public draft to attract interoperability feedback. Discussion remains public during implementation and dogfooding. Acceptance authorizes implementation into the Community Working Draft; it does not publish 0.8.0 as stable or claim community consensus.

The project should retain 30 days of public visibility before a stable 0.8.0 release unless a separate, documented release decision approves an exception.

## Problem

MCP Description 0.7.0 assumes one MCP revision through `info.protocolVersion`, models one unscoped capability object, requires at least one primitive, and permits Tool definitions without `inputSchema`. MCP `2026-07-28` changes discovery, lifecycle, extension, task, subscription, and schema behavior. A simple version-enum addition would neither describe servers that span revisions nor provide deterministic protocol-specific validation.

At the same time, copying each new MCP request, response, notification, or transport mechanism into mcpdesc would couple a static contract format to wire choreography and create fields without durable semantic value.

## Goals

- Describe one logical server across supported MCP protocol revisions.
- Produce exactly one deterministic effective contract for a selected revision.
- Reject protocol revisions whose semantics mcpdesc 0.8.0 cannot validate.
- Preserve durable capability meaning across changes in MCP wire mechanisms.
- Represent genuine protocol-specific differences without duplicating a whole server description.
- Align Tool `inputSchema` requirements with every supported MCP revision.
- Enable projection and merge tooling with explicit, testable set semantics.
- Keep runtime dumps honest about what was actually observed.

## Non-goals

- Mirror every JSON-RPC request, result, error, notification, or header.
- Define arbitrary variants for transports, tenants, authorization contexts, feature flags, or client capabilities.
- Define mcpdesc-specific tool errors.
- Standardize merge serialization or source-format preservation.
- Add elicitation declarations in this proposal; that design requires separate review.
- Define the security model; named schemes and requirements are handled by a separate proposal.
- Modify the MCP Toolkit or other downstream implementations in this repository.

## Proposed normative behavior

### 1. Supported MCP protocol revisions

mcpdesc 0.8.0 supports exactly:

- `2024-11-05`;
- `2025-03-26`;
- `2025-06-18`;
- `2025-11-25`;
- `2026-07-28`.

The 0.8.0 JSON Schema MUST use this closed enumeration. A document containing an unknown or later revision is invalid. Supporting a later MCP revision requires a new mcpdesc release whose schema, semantic rules, tests, and migration guidance can account for that revision.

This deliberately favors verifiable conformance over speculative forward compatibility.

### 2. Root protocol coverage

Remove `info.protocolVersion` and add required root `protocolVersions: string[]`. The array MUST be non-empty, contain unique values, and contain only supported revisions.

Root coverage means the revisions described by the document. It does not prove that the server supports no other revisions. A runtime observation MUST NOT add a revision merely because discovery advertises it when that revision's contract was not observed or supplied by authoritative design metadata.

### 3. Protocol-scoped declarations

Transports, Capabilities Objects, Tools, Resources, Resource Templates, and Prompts MAY contain `protocolVersions`.

For a root version set `R`, the effective scope of a top-level declaration `x` is:

```text
S(x) = x.protocolVersions when present; otherwise R
```

An explicit scope MUST be a non-empty subset of `R`.

For a nested scoped declaration `y` with parent `x`:

```text
S(y) = y.protocolVersions when present; otherwise S(x)
```

An explicit nested scope MUST be a non-empty subset of `S(x)`. It is invalid for a child to become applicable where its parent is not applicable.

Omitting a scope therefore means the complete effective parent scope. It does not mean an unspecified or empty scope.

### 4. Set constraints

The following constraints make each effective view deterministic:

1. **Transport coverage:** the union of effective transport scopes MUST equal the root version set. Transport scopes MAY overlap because more than one transport can support the same revision.
2. **Capability uniqueness:** effective Capabilities Object scopes MUST be pairwise disjoint. At most one capability declaration may apply to a revision.
3. **Primitive uniqueness:** declarations of the same primitive kind with the same effective identifier MUST have pairwise-disjoint scopes.
4. **Child containment:** every nested scope MUST be a subset of its effective parent scope.

Effective identifiers are:

- Tool: `name`;
- Prompt: `name`;
- Resource: `uri`;
- Resource Template: `uriTemplate`.

Different identifiers may overlap because they represent different primitives.

An unscoped declaration has scope `R`; consequently it overlaps every explicitly scoped declaration of the same primitive identifier. Authors must split such a declaration into disjoint variants rather than combining an unscoped default with scoped exceptions.

### 5. Effective protocol view and projection

For version `V`, projection `P_V(D)` includes each scoped declaration whose effective scope contains `V` and excludes all other scoped declarations.

A conforming single-version projection tool MUST:

1. validate the source document;
2. require `V` to occur in root `protocolVersions`;
3. set root `protocolVersions` to `[V]`;
4. retain applicable transports, capabilities, primitives, and nested declarations;
5. remove `protocolVersions` from retained declarations because their applicability is now unambiguous;
6. preserve semantically significant empty values and inheritance, including security overrides defined by the security proposal;
7. optionally omit empty primitive collections; and
8. validate the projected document structurally and semantically against MCP revision `V`.

Projection produces an ordinary conforming mcpdesc document, not a second format. “Flat” means one root protocol revision and no scoped alternatives.

Projection MUST NOT materialize transport-dependent inherited values onto a primitive unless a transport is also selected and the operation explicitly defines such resolution.

### 6. Merge tooling

A merge tool MAY construct an aggregate document from single-version or multi-version descriptions. It MUST validate every input and MUST report a conflict rather than guess when the inputs cannot be represented faithfully.

A conforming merge algorithm SHOULD:

1. project inputs into individual protocol views;
2. require compatible logical server identity and unscoped metadata;
3. union root protocol-version sets;
4. group primitives by kind and effective identifier;
5. collapse equivalent declarations and union their scopes;
6. retain differing declarations as disjoint scoped variants;
7. collapse semantically equivalent capability and transport declarations;
8. omit a scope when it equals the complete effective parent scope; and
9. validate the aggregate result.

If inputs cover the same revision, their effective views MUST be equivalent or the merge fails. Conflicting `info`, `instructions`, root extension values, or other unscoped values also cause failure unless a future specification defines a lossless representation for the difference.

For every merged source view `D_V`, the effective-contract invariant is:

```text
P_V(merge(D_1, ..., D_n)) is semantically equivalent to D_V
```

Round trips need not preserve property order, redundant scopes, array order where semantically insignificant, or the author's original choice between an omitted scope and an explicit full-parent scope.

The projection semantics are normative. Merge serialization, canonicalization, and command-line interfaces remain tooling concerns in 0.8.0.

### 7. Capabilities

Change root `capabilities` from one object to an optional array of Capabilities Objects. Capability scopes obey the pairwise-disjoint rule above.

Keep the following durable notification-related semantics:

- `tools.listChanged`;
- `prompts.listChanged`;
- `resources.listChanged`;
- `resources.subscribe`.

These fields describe observable server behavior, not the MCP RPC or delivery mechanism. Do not add first-class fields for `subscriptions/listen`, subscription acknowledgements, cancellation, progress, or lifecycle notifications solely because those messages exist.

Add `capabilities.extensions` where the applicable MCP revision defines MCP capability extensions. Its keys MUST follow the MCP mandatory-prefix metadata naming rules and its values MUST be JSON objects. Unknown syntactically valid identifiers are accepted and preserved. Reserved namespace misuse is a semantic error.

Core Tasks in MCP `2025-11-25` and the Tasks extension in MCP `2026-07-28` are distinct declarations and MUST NOT be automatically reinterpreted as one another.

### 8. Root instructions

Add one optional root `instructions` string representing durable MCP server guidance. It is not protocol-scoped in 0.8.0. Material changes to instructions are contract-significant and SHOULD be included in semantic comparison and changelog tooling.

If instructions differ materially by revision or runtime context, authors must publish separate descriptions or use a specification extension. A merge tool must report incompatible instructions rather than select one.

### 9. Tool input schemas

Every Tool MUST contain `inputSchema`. This matches every MCP protocol revision supported by mcpdesc 0.8.0. Absence is a protocol-conformance error and MUST NOT be interpreted as evidence that a tool accepts no arguments.

The schema root MUST describe an object. Documentation and examples MUST distinguish three forms.

#### Closed no-parameter schema

```json
{
  "type": "object",
  "additionalProperties": false
}
```

This accepts only an empty object and is the RECOMMENDED form for a tool with no parameters.

#### Open unspecified-parameter schema

```json
{
  "type": "object"
}
```

This accepts any object, including objects with undeclared properties. It is valid but NOT RECOMMENDED because it offers little validation, documentation, code-generation, or model-guidance value. Adding `"properties": {}` does not close the object.

#### Declared-parameter schema

```json
{
  "type": "object",
  "properties": {
    "query": { "type": "string", "minLength": 1 }
  },
  "required": ["query"],
  "additionalProperties": false
}
```

This declares named parameters. `additionalProperties: false` is needed when undeclared properties must be rejected; declared properties alone do not close the object.

For MCP `2026-07-28`, validators MUST accept the full applicable JSON Schema 2020-12 vocabulary, including references, composition, and conditionals, plus MCP-defined schema annotations such as `x-mcp-header` where valid. Earlier revision views MUST be checked according to their applicable MCP schema rules.

### 10. Zero-primitive descriptions

A document MAY omit all of `tools`, `resources`, `resourceTemplates`, and `prompts`. This can describe a server under development, a legitimately empty server, or an authorization-scoped observation. Absence MUST NOT be interpreted as proof that no other runtime context can expose primitives.

### 11. Observed and aggregate descriptions

A runtime dump represents an observed effective view and SHOULD normally contain one protocol revision. It MUST NOT infer unobserved primitive inventories or claim a revision merely from server advertisement.

A curated aggregate may combine authoritative definitions or multiple observed views. Aggregation does not justify inferring hidden primitives, minimum OAuth scopes, or other runtime policy from insufficient evidence.

## Schema impact

The 0.8.0 schema will:

- require root `protocolVersions` using the closed supported-revision enum;
- remove `info.protocolVersion`;
- add reusable protocol-scope definitions to applicable objects;
- change `capabilities` to an array;
- add root `instructions`;
- permit zero primitive collections;
- require Tool `inputSchema`;
- permit the applicable Tool JSON Schema vocabulary; and
- add structural constraints where JSON Schema can express them.

Cross-object set coverage, pairwise disjointness, child containment, effective identifier uniqueness, MCP-revision field legality, and reserved extension namespace checks require semantic validation.

The 0.7.0 schema remains immutable. `schemas/latest.json` remains 0.7.0 until an explicit stable release. A mutable versioned 0.8.0 schema is required after proposal acceptance so the Community Working Draft can be implemented and dogfooded.

## Examples

### Disjoint primitive variants

```json
{
  "protocolVersions": ["2025-11-25", "2026-07-28"],
  "tools": [
    {
      "name": "run_job",
      "protocolVersions": ["2025-11-25"],
      "inputSchema": {
        "type": "object",
        "additionalProperties": false
      },
      "execution": { "taskSupport": "optional" }
    },
    {
      "name": "run_job",
      "protocolVersions": ["2026-07-28"],
      "inputSchema": {
        "type": "object",
        "additionalProperties": false
      }
    }
  ]
}
```

The two declarations share an identifier but are valid because their scopes are disjoint. An unscoped third `run_job` declaration would overlap both and make the document invalid.

### Overlapping transports

```json
{
  "protocolVersions": ["2025-11-25", "2026-07-28"],
  "transports": [
    {
      "type": "stdio",
      "command": "example-server"
    },
    {
      "type": "streamable-http",
      "url": "https://example.com/mcp",
      "protocolVersions": ["2026-07-28"]
    }
  ]
}
```

The unscoped stdio transport covers both root revisions. The HTTP transport may overlap it for `2026-07-28` because transport alternatives are allowed.

## Compatibility

Classification: **breaking**.

Breaking changes include removal of `info.protocolVersion`, required root coverage, capability-array conversion, the closed protocol enum, required Tool `inputSchema`, and protocol-aware semantic constraints. This is justified because mcpdesc is pre-1.0, 0.7.0 cannot model deterministic multi-revision contracts, and retaining aliases would create ambiguous sources of truth.

Unknown future MCP revisions that a 0.7.0 schema happened to accept are rejected by 0.8.0. This is intentional: syntactic preservation without semantic validation is not 0.8.0 conformance.

## Migration

A 0.7.0 migration tool should:

1. move `info.protocolVersion` to root `protocolVersions` as a one-item array;
2. wrap a present `capabilities` object in an array;
3. preserve primitive collections and metadata;
4. require author intervention for every Tool missing `inputSchema`;
5. insert a closed no-parameter schema only when the author confirms that the Tool accepts no arguments, recording repair provenance when operating in a repair mode;
6. reject or separately retain documents using unsupported MCP revisions; and
7. validate the migrated document structurally and semantically.

A migration tool MUST NOT silently turn a missing Tool schema into an open or no-parameter schema because the omission does not reveal author intent.

## Security and privacy considerations

- Projection and merge tools must preserve extension data and semantically significant overrides rather than broadening a contract silently.
- Runtime dumps may expose primitives or instructions visible only to the observing authorization context and must not claim exhaustive visibility.
- Tool schemas and `x-mcp-header` annotations can expose sensitive parameter intent; authors and consumers must follow applicable MCP security guidance.
- Tool annotations remain untrusted hints and are not authorization controls.
- The named security-scheme and requirement design receives separate review.

## Alternatives considered

### Keep an open protocol-version string

Rejected. A validator cannot claim complete MCP semantic conformance for an unknown revision. A new MCP revision may change field meaning, schema dialect, or constraints that 0.8.0 does not know.

### Publish one complete description per revision only

Rejected as the sole representation. It duplicates stable metadata and makes cross-version comparison harder. Projection still provides this convenient view.

### Nest complete descriptions under version profiles

Rejected. It duplicates most documents and obscures shared durable semantics.

### Permit overlapping capability or same-identifier primitive scopes

Rejected. Projection would produce ambiguous declarations for one revision.

### Model notification RPCs directly

Rejected. The same durable behavior uses different MCP mechanisms across revisions, and wire-message catalogues do not form a stable static contract.

### Keep Tool `inputSchema` optional

Rejected. All supported MCP revisions require it, and omission cannot distinguish no parameters from unknown parameters.

## Open questions

No architectural question blocks review. Exact schema factoring, diagnostic codes, canonical ordering, and command-line interfaces are implementation details that must preserve the normative behavior above.
